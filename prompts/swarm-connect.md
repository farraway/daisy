## Trigger

Read the full `$DAISY_ROOT/prompts/swarm-connect.md` when:
- The user invokes `/daisy swarm connect [<swarm>]` or says "connect to the swarm"
- The user asks to be briefed on a running Daisy swarm and then to steer it from this session

## Rules

1. **Find the swarm, then work in its clone.** Run `daisy swarm list`: it runs anywhere, writes nothing and names each swarm this machine runs (`<owner>/<repo> on <forge-host>`), its clone, its home and whether it is paused. Take the swarm the argument names (its `<owner>/<repo>`, its repository's name or its clone's path); without one, the swarm marked `here`, else the only one listed; with several, show the list and ask which. Every swarm command runs in the clone (`cd <clone> && daisy swarm status`); when the clone is `not recorded` or `not a clone of it now`, ask the user where it is. `daisy log` and `daisy metrics` run in the Daisy workspace the session began in.
2. **Brief first, reading only.** Before anything else, report in this order, quoting a run's or a note's own words where they matter:
   - **Since the last connect:** `daisy swarm journal` prints the journal's lines after the one last marked seen (on a first connect, its newest day's). Summarize them per issue (`daisy swarm journal --issue <n>` prints one issue's lines alone): what ran, what it produced, what failed or faulted and why. A run's files are under `runs/<n>-<role>-<k>/` in the state directory `daisy swarm status` names on its `State:` line.
   - **What waits for the user:** `daisy swarm status`. Its `Waiting for you` line, each item with the decision it asks and the evidence for it, as the `swarm` skill's rule 2 reads them (`question` and `blocked` first: a member waits on each); its `Held` line; the `State:` line's pause and its reason (two swarm faults in a row pause the swarm) and the owner's held batch; Throughput's faults and failures.
   - **What you may do unasked:** `AUTHORITIES.md` at the clone's top, the maintainer's standing authorities for this connect, each under its label (`A1`, …). Name each label and what it grants; with no file, say that nothing is granted.
   - **The metrics since the last model or prompt change:** that change is the clone's newest commit to `swarm.json` (the personas) or `prompts/`, `git -C <clone> log -1 --format='%cI %h %s' -- swarm.json prompts/`. Run `daisy metrics --swarm <owner>/<repo> --since <its time>`, and `daisy metrics --swarm <owner>/<repo>` to compare: runs, tokens, cost and estimate per model, since the change and in all. When the swarm's home (`daisy swarm list`) is not this workspace's (`daisy status`), its rows are in that home: say so and leave the metrics out.
3. **Then mark the journal seen.** Run the `daisy swarm journal --mark <run>` line the journal printed last, which names the run of its last line shown. The mark is this connect's own record in the swarm's state directory: it needs no confirmation and no log.
4. **Converse through the `swarm` skill.** After the briefing, answer and act as `skills/swarm/SKILL.md` says, for every question and every verb: run a write only on the user's yes to it, as its rule 3 says; under this connect, an authority the briefing named is that yes for a write wholly within it. Never `daisy swarm apply` or `daisy swarm init`, no forge call of your own, no secret read or named but the variable `DAISY_MAINTAINER_TOKEN`.
5. **Log each write** as the `swarm` skill's rule 8 says, running `daisy log` in the workspace the session began in (rule 1), not in the clone: `daisy log --co-author "<your line>" "swarm: accepted the plan of #12"`. Reading is not logged.
6. **Say what you could not read.** A briefing command that fails is reported with its error and the briefing goes on without that part; never fill the gap with a guess.
