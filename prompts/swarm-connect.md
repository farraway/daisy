## Trigger

Read the full `$DAISY_ROOT/prompts/swarm-connect.md` when:
- The user invokes `/daisy swarm connect [<swarm>]` or says "connect to the swarm"
- The user asks to be briefed on a running Daisy swarm and then to steer it from this session

## Rules

1. **Find the swarm, then work in its clone.** Run `daisy swarm list`: it runs anywhere, writes nothing and names each swarm this machine runs (`<owner>/<repo> on <forge-host>`), its clone, its home and whether it is paused. Take the swarm the argument names (its `<owner>/<repo>`, its repository's name or its clone's path); without one, the swarm marked `here`, else the only one listed; with several, show the list and ask which. Every swarm command runs in the clone (`cd <clone> && daisy swarm connect`); when the clone is `not recorded` or `not a clone of it now`, ask the user where it is. `daisy log` runs in the Daisy workspace the session began in.
2. **Brief first, reading only.** Run `daisy swarm connect` in the clone: it writes nothing and prints the briefing's data as one report. Report from it, in its order, quoting a run's or a note's own words where they matter:
   - **Since the last connect:** its journal lines, grouped by issue. Summarize each issue's: what ran, what it produced, what failed or faulted and why. A run's files are under `runs/<n>-<role>-<k>/` in the state directory its `State:` line names.
   - **What waits for the user:** its `Waiting for you` line, each item with the decision it asks and the evidence for it, as the `swarm` skill's rule 2 reads them, starting from the gate note printed under it (the reason and the decision's verbs; where none is printed, from the issue's runs) (`question` and `blocked` first: a member waits on each); its `Held` line; the `State:` line's pause and its reason (two swarm faults in a row pause the swarm) and the owner's held batch; the faults and failures on its `Runs` line.
   - **What the swarm answers itself:** its `Questions the swarm answers` part: each open question and the architect or owner it waits on, not the user.
   - **What you may do unasked:** its `Authorities` part quotes `AUTHORITIES.md`, the maintainer's standing authorities for this connect, each under its label (`A1`, …). Name each label and what it grants; when it says `none granted`, say that nothing is granted.
   - **The metrics since the last model or prompt change:** its `Metrics` part, per model, since the clone's newest commit to `swarm.json` or `prompts/` and in all: compare runs, tokens, cost and estimate. When its first line says `none (<why>)`, give that reason and leave the metrics out; a part that says `none` has no runs in it; with no commit to `swarm.json` or `prompts/`, give the totals alone.
3. **Then mark the journal seen.** Run the `daisy swarm journal --mark <run>` line the report printed (after rule 6's fallback, the one `daisy swarm journal` printed), which names the newest journal line shown, whatever the grouping; with none printed, there is nothing to mark. The mark is this connect's own record in the swarm's state directory: it needs no confirmation and no log.
4. **Converse through the `swarm` skill.** After the briefing, answer and act as `skills/swarm/SKILL.md` says, for every question and every verb: run a write only on the user's yes to it, as its rule 3 says; under this connect, an authority the briefing named is that yes for a write wholly within it. Never `daisy swarm apply` or `daisy swarm init`, no forge call of your own, no secret read or named but the variable `DAISY_MAINTAINER_TOKEN`.
5. **Log each write** as the `swarm` skill's rule 8 says, running `daisy log` in the workspace the session began in (rule 1), not in the clone: `daisy log --co-author "<your line>" "swarm: accepted the plan of #12"`. Reading is not logged.
6. **Say what you could not read.** When `daisy swarm connect` fails, report its error, then brief from whichever of `daisy swarm status`, `daisy swarm journal` and `AUTHORITIES.md` at the clone's top still answers, naming the parts left out; never fill a gap with a guess.
