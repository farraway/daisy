## Trigger

Read the full `$DAISY_ROOT/prompts/plan.md` when:
- User invokes `/daisy plan`, `/daisy execute`, `/daisy archive`, `/daisy resume`, `/daisy plan spec`, or `/daisy plan pickup`
- User says "Daisy, plan ...", "Daisy, execute ...", "Daisy, archive ...", "Daisy, spec out ...", or "Daisy, pick up ..."
- `PLAN.md` exists at the workspace root and any plan-related work is in progress
- A `{slug}_PLAN.md` draft exists at the workspace root

**Plan workflow:**
- `plan <description> [+project]` → create PLAN.md, enter collaborative planning mode
- `plan spec <description> [+project]` → create an unregistered draft (`{slug}_PLAN.md`) directly at the workspace root — no `$DAISY_HOME/plans/` copy, no `PLAN.md` symlink. Multiple drafts can coexist while deciding which (if any) to pursue.
- `plan pickup <path>` → promote a local spec draft into a tracked plan: copies it into `$DAISY_HOME/plans/`, creates the `PLAN.md` symlink
- `execute PLAN.md` → implement the plan in batches of steps, one fresh sub-agent per batch, each batch reviewed and verified before the next
- `archive PLAN.md` → move completed plan to archive
- `resume PLAN.md` → verify state from a previous session, confirm resumption point, continue execution

---

## Rules

1. **Research before scaffolding.** Before filling in PLAN.md sections, read what already exists relevant to the task. Identify what's essential (inherent to the problem) vs. accidental (artifact of the current approach). Confirm the research summary with the user before scaffolding.
2. **No implementation during plan mode.** During `/daisy plan`, only edit `PLAN.md`; do not write any implementation code until the user confirms the plan is ready.
3. **Collaborate until confirmed.** Present the Open Questions list via `AskUserQuestion` (the client's native Q&A UI), including a final question equivalent to "Ready to execute?"; fall back to prose ending in "Ready to execute? (yes/no)" only when `AskUserQuestion` is unavailable. Precede the question with the plan summary required by rule 19. Do not proceed to execution without confirmation.
4. **Prefer spec-mode when the shape isn't settled yet.** Use `plan spec` instead of `plan` when exploring multiple candidate approaches before committing to one, or when it's not yet clear this deserves a tracked Daisy plan at all. Promote to a real plan with `plan pickup` once a direction is chosen.
5. **Read praxis.md before each step.** During `/daisy execute`, the step agent reads `$DAISY_ROOT/prompts/praxis.md` as the quality guide before implementing its step.
6. **Check off steps immediately.** The orchestrator marks each step `- [x]` in `PLAN.md` as soon as it has verified its batch's hand-back (rule 23), before moving on; a step its batch stopped on stays unmarked (rules 22 and 24).
7. **Stop and report when blocked.** Do not skip steps or work around blockers silently; surface them explicitly.
8. **Out-of-scope work goes to Deferred.** When a need surfaces outside the current step, add it to Deferred — do not implement it partially or silently drop it. A step agent names it in its hand-back as a Deferred candidate and the orchestrator adds it (rule 20). A review's out-of-gate remark is not a candidate: it goes to the hand-back too, and the orchestrator adds one to Deferred only when it names a defect at a file and line (rule 22).
9. **Log each verified step, and before the session closes.** `prompts/daisy.md` rule 6 says when to log; under `/daisy execute` and `/daisy resume` the orchestrator logs, via `daisy log`, each step as soon as it has verified its batch's hand-back (rule 23), each stop of rule 24 with its reason, and, after the last step, a summary. A step agent leaves the journal to the orchestrator (rule 20).
10. **Warn before archiving incomplete plans.** If `**Status:**` is not `built`, confirm with the user before archiving.
11. **Archive only applies to Daisy plans.** `/daisy archive` requires a `PLAN.md` symlink in the workspace. Plans created by Claude's `/plan` mode (stored in `~/.claude/plans/`) are not Daisy plans — there is nothing to archive.
12. **Calibrate process to task complexity.** Skip the plan workflow for simple, contained changes (a one-liner, a rename, a config tweak) — just do them directly. Use one research pass + plan for single-file features. Use full RPI with human checkpoints for cross-file or cross-repo work. Reserve multiple research iterations for complex refactors.
13. **Steps must name files; complex steps show code.** Every step should identify the specific files (and line ranges where known) that will change. For non-trivial changes, include a brief before/after code snippet. Vague steps ("refactor auth module") give the agent nothing to anchor on — and an error in the plan is an error in every line that follows from it. Every step ends with `Claim:` one sentence the reviewer can refute by a command, a test name or two quoted passages, naming its oracle (testing skill, The claim). A step is one claim, about one screen of diff: a claim whose "and" joins two changes is two claims, so split it into two steps; an "and" between checks of one change ("cases 54 and 55 pass") is not. "Consistent", "traceable" and "complete" are adjectives, not claims: write the check that would show them false (`` `grep -c "T11" docs/swarm.md` gives the same count in §5, §6, §13 and the diagram ``).
14. **Surface repeated corrections; do not compound them.** If you have made the same mistake twice on a step, stop. Tell the user what you've tried and why it keeps failing; ask whether to compact what's been learned and start the step fresh. Do not continue correcting in-place — a history of corrections degrades trajectory and primes further failure.
15. **Resume by verifying state, not assuming it.** When picking up an in-progress plan from a previous session, do not assume completed steps are correct — verify. Check git log, today.md, and spot-check key files. Summarize what is confirmed, what is uncertain, and where work was interrupted. Present the plan summary required by rule 19 alongside that verification, then confirm with the user before continuing.
16. **Ask before deleting a picked-up spec's original.** `daisy plan pickup` never deletes the original `{slug}_PLAN.md` itself — after a successful pickup, ask the user whether to delete it now that its content is tracked via the `PLAN.md` symlink, and only run `rm` if they confirm.
17. **Resolve the real path before writing `PLAN.md`.** `PLAN.md` is a link: write the plan at the path `daisy files plan` prints, as `prompts/daisy.md`'s Trigger block says of every Daisy file, for every edit during `execute`, `resume` and `archive`. The rule binds the main agent, the orchestrator during `execute` and `resume`: it alone writes the plan, and a step agent never does (rule 20).
18. **Live-test auto-committing commands only against a hermetic fixture.** Never exercise a command or script that auto-commits (or otherwise mutates) against a real, in-use home. Use `daisy test`'s fixture harness, or a scratch home, registry and workspace under a temp directory (`DAISY_CONFIG` and `DAISY_LOCAL` pointed there before `daisy home new <fixture-home>`, and `daisy init <fixture-home>` run in a scratch workspace; praxis rules 14–15), and tear it down afterward.
19. **Show the plan before asking for approval.** Every readiness question — `/daisy plan`'s "Ready to execute?" and `/daisy resume`'s "Ready to resume from Step N?" — must be immediately preceded, in the same response, by a summary the user can answer from without opening the file. In this order: (1) the plan name and its metadata (created date, status); (2) one line on what the plan accomplishes; (3) every step, one line each, optionally followed by a sentence or two on what it entails and any constraint on it — every step, not an abridged selection; (4) risks, each with its mitigation; (5) open questions. A question the user must open a file to answer defeats the point of asking it.
20. **Execute each batch in a fresh sub-agent.** During `/daisy execute` and `/daisy resume`, the main agent orchestrates and does not implement. It groups the steps into batches (rule 22) and for each batch briefs a fresh sub-agent, the step agent, not a fork, with the steps written into the brief, not the plan's path to read: the plan's Goal in a sentence, the Non-goals, each step's text, the Decisions that name a step or bear on it, and the Constraints; and with `$DAISY_ROOT/prompts/praxis.md`, the `testing` skill, the review and the gate (rule 22), the reviewers' model and effort (rule 21), the hand-back's shape (rule 25), that it neither reads nor writes the plan file and that it leaves the journal to the orchestrator (rule 9). The step agent states each step's claim, does the steps in order, one commit per step (none for a step it stops on, rule 24), runs the batch's review (rule 22) and hands back each step's decisions, Deferred candidates and open questions, and any rule it proposes (praxis rule 16) marked as a proposed rule. A step's change to a spec is the line in the section (and the decision record, where the project keeps them) it implements that says it is built, plus any sentence the change makes false; a fuller reconciliation of the spec is a step of its own. The orchestrator writes the plan: after verifying the hand-back (rule 23) and before the metrics and the log, it marks each step `- [x]` (not one the batch stopped on), records the decisions in Decisions, the Deferred candidates and the review's leftovers that rule 22 sends to Deferred in Deferred, and the open questions in Open Questions. A proposed rule goes to Open Questions marked **Rule question**, asked alone at the next stop or at the run's end; it is not itself a stop.
21. **Ask which models run the steps and the reviews.** During `/daisy plan`, ask the user which model and effort level the step agents and the review agents use, and record the answer in Decisions. When `/daisy execute` or `/daisy resume` finds no answer in Decisions (a plan reached through `plan spec` and `pickup`), ask it before launching the first batch, and record the answer in Decisions. Whenever you ask it, recommend a Sonnet-class model for the review agents: it is the default, and another model reviews only when Decisions names a reason for it (the user's answer is reason enough). Each batch's brief names its reviewers' model and effort. The reason for the default: `$DAISY_ROOT/docs/plan.md`, Models and step size.
22. **Build in batches, to the claim; review each batch, fix, then check.** The orchestrator groups the plan's steps, in order, into batches, and one step agent builds a batch's steps in order, one commit per step, each with its claim's test written red first and its probes (the `testing` skill) where the step has a test (rule 20). A step builds its claim and nothing beyond: an edge case the claim does not name goes to the hand-back as a Deferred candidate, not into the code; where the spec is silent, the step takes the simplest reading consistent with it and names the alternative as an open question. The gate is the project's checks and tests and `daisy healthcheck --force`, and a commit follows only a green gate. Between a batch's commits it runs cached (in Go, the test cache kept); once per batch, after the review and before the hand-back, it runs uncached (in Go, `go clean -testcache` first), and so does the orchestrator's verification (rule 23). After the batch's last step, a separate review agent attacks the batch's range, with each step's intent and claim stated: a pass tests the claims. A finding is in gate only when the reviewer reproduces it (quotes the code or passage and shows the failure against the step's text or a rule) and it falls in one of four classes: the claim fails, a required item is missing or wrong, a test is red, a document contradicts another. Every pass's brief names these four and adds none, not even a past finding's type. A green test is not red, and a missing one is in gate only when the step's text names it; a contradiction is in gate only when the range introduced it (compare with `git show <base>:<file>`, `<base>` the commit the range starts from); a hole two passages leave open goes to Open Questions (through the hand-back, rule 25). Out of gate are style, anything outside the steps' stated claims, and a finding that needs an arrangement the project's own contract does not support (in Daisy's root, a link a user makes into it). Pass 1, a review agent on rule 21's model (a Sonnet-class one by default), reviews and fixes: it classifies every finding before fixing any, in gate or out of gate, fixes each in-gate one itself (code, tests, prose), runs the cached gate, commits its fixes and reports each finding with its fix. Pass 2, a fresh agent on the same model, reads only pass 1's fix commits: whether each fix is right and whether it introduced an in-gate defect in the lines it changed; it starts no new hunt. With no fix commit there is no pass 2. Then the review closes. A leftover that does not change behaviour (every claim holds and no test is red) goes to Deferred, and so does an out-of-gate remark that names a defect at a file and line: the step agent reports them in its hand-back and the orchestrator adds them (rule 20); any other remark ends in the hand-back. A behaviour finding still open (a claim fails or a test is red) gets one more fix and one more check of it. Still open, the batch stops: the step agent hands back the finding with its proposed fix uncommitted, and the orchestrator takes it to the user, marks no step the finding falls in and runs no further pass. The reasons and the history: `$DAISY_ROOT/docs/plan.md`, The review gate.
23. **Verify every hand-back before the next batch.** The orchestrator checks each step's claim, runs the gate uncached itself (rule 22: the checks, the tests and `daisy healthcheck --force`), runs the project's hygiene check where it has one, and confirms the commits before it writes the plan (rule 20) and launches the next batch. For a hand-back stopped by the review (rule 22) or at another stop of rule 24, it confirms that nothing past the stop is committed (a step stopped at a stop of rule 24 has no commit; at the review's stop, the proposed fix is uncommitted), and still records the batch's Decisions and Deferred. It never re-runs for a sub-agent an action the permission gate refused the sub-agent: it reports the refusal to the user verbatim and stops.
24. **Run unattended between the stops.** Do not ask the user before each step. Stop when the run needs something only the user can give and the plan does not record: a decision of theirs (rule 21's answer when Decisions has none; a rearchitecture that crosses a decision they made, praxis rule 4), an approval (a hard-to-reverse or outward-facing action the plan does not call for, such as a force-push, a deletion or a publication; a step the plan gives the user), or a way past a block (a batch stopped by its review, rule 22; the same mistake twice, rule 14; a permission refusal, rule 23). The plan's own checkpoints are stops too.
25. **Hand back in one shape.** The step agent's report gives, for each step: the claim and the probes that showed its tests can fail (the test red first, then red again with the change reverted); lines added and deleted; its commit; the decisions it made, each with the alternative considered; its Deferred candidates (rule 8) and open questions, a rule it proposes marked as one (rule 20). For the batch: each review pass with its findings, each in-gate one with its fix and the fix's commit, and its out-of-gate remarks, each with the file and line the reviewer gave (rule 22); the leftovers bound for Deferred; at a stop, the stop and its reason, the step or the open finding it stopped on, and the proposed fix left uncommitted, for a metrics row with `--outcome "stopped: <stop>"`; the verification lines (the uncached gate, health check, hygiene); the batch's commit range and the repository it is in; the tokens used, the step agent's (per step where it can count them apart) and each reviewer's, each with its model and effort.

# Daisy — Plan Workflow

## /daisy plan \<description\> [+project]

1. Call `daisy plan new "<description>" ["+project"]`
2. Enter plan mode — only edit `PLAN.md`; do not write implementation code.
3. **Research phase:** Read what already exists relevant to the task. Identify: (a) what already solves part of this, (b) what's essential to the problem (inherent) vs. accidental (artifact of current approach). Write findings into the `## Research` section of `PLAN.md`. Ask: **"Research summary confirmed — proceed to planning? (yes/no)"**
4. Scaffold plan sections from conversation context: fill in Goal, Non-goals, Constraints; leave Steps as placeholder checkboxes.
5. If a `+project` tag was given: update `.daisy/projects/{project}.md` — add a Plans section with a relative link and status `in progress`.
6. Ask which model and effort level the step agents and the review agents use; record the answer in Decisions (rule 21).
7. Close each planning round with the plan summary (rule 19) and the Open Questions through `AskUserQuestion`, the last of them "Ready to execute?" (rule 3).

## /daisy plan spec \<description\> [+project]

1. Call `daisy plan new --spec "<description>" ["+project"]` — writes `{slug}_PLAN.md` directly to the workspace root. No `PLAN.md` symlink is created and nothing is registered in `$DAISY_HOME/plans/` yet.
2. Same collaborative planning discipline as `/daisy plan` (rules 1–3) — only edit the draft file, research before scaffolding, end with Open Questions.
3. Multiple specs can coexist in the same directory (each has its own `{slug}_PLAN.md`) — useful for sketching more than one candidate approach before choosing.
4. When a direction is chosen, promote it: `/daisy plan pickup <path-to-spec>`.

## /daisy plan pickup \<path\>

1. Call `daisy plan pickup "<path>"` — copies the spec into `$DAISY_HOME/plans/` with the standard timestamp+slug filename and creates the `PLAN.md` symlink. The original file at `<path>` is left untouched by the command.
2. Ask the user: **"Delete the original spec file now that it's tracked? (yes/no)"** Run `rm <path>` only if they confirm (rule 16).
3. From here the plan behaves like any other — proceed with `/daisy execute` when ready.

## /daisy execute PLAN.md

0. Resolve the plan's real path with `daisy files plan` and write every change below there (rule 17).
1. Read `PLAN.md`; confirm at least one unchecked `- [ ]` step exists, and that Decisions records rule 21's answer (ask it if not, recommending a Sonnet-class model for the review agents, rule 21).
2. Update `**Status:** executing` in the frontmatter block (write to the resolved real path).
3. Group the steps, in order, into batches and work through the batches, each in a fresh sub-agent (rules 20 and 22) briefed with its steps written in, not the plan's path (the plan's Goal in a sentence, the Non-goals, each step's text, the Decisions that name a step or bear on it, the Constraints), and with `$DAISY_ROOT/prompts/praxis.md`, the `testing` skill, the review and the gate (rule 22), the reviewers' model and effort (rule 21), the hand-back's shape (rule 25), that it neither reads nor writes the plan file and that it leaves the journal to the orchestrator (rule 9).
4. The step agent, which neither reads nor writes the plan file nor writes the journal, reads `praxis.md` and, for each step in order, states its claim, does it and commits it after a green gate (none for a step it stops on, rule 24); then it runs the batch's review (rule 22), runs the gate uncached and hands back, with each step's decisions, Deferred candidates and open questions in the hand-back (rule 25).
5. Verify the hand-back (rule 23), then write the plan (to the resolved real path): mark each step `- [x]` (not a step the batch stopped on), record the decisions in Decisions, the Deferred candidates in Deferred with the review's leftovers and each out-of-gate remark the hand-back reports that names a defect at a file and line (rule 22), and the open questions in Open Questions, a proposed rule among them marked **Rule question** (rule 20); then record the metrics with `daisy metrics add`: for each step a `--role step` row, `--step <n> --range <its commit> --repo <its repository>` with the step agent's model, effort and tokens; for the batch one `--role review` row for each reviewer model and effort its passes used, `--step` its steps joined by `+` (`--step 4+5`), with that model and effort, `--review-rounds` the passes, `--review-effect` the in-gate findings they fixed and their tokens summed (no range, so no lines). A step the batch stopped on keeps the same two rows as a finished step, its step row (no range when it has no commit) and its batch's review row, each with `--outcome "stopped: <stop>"` (`stopped: review` at the review's stop). Then log each step via `daisy log` (rule 9), before launching the next batch; do not ask the user between batches.
6. Stop and report at the stops of rule 24, or if blocked; do not skip steps or work around blockers silently. At the run's end, record one `--role orchestrator` row (`--step` the last step the run verified) with the orchestrator's own model, effort and tokens when it can count them, else empty.
7. On all steps complete: append ` *Built*` to the H1 title; update `**Status:** built` (write to the resolved real path).
8. Log execution summary to `today.md` via `daisy log`.

## /daisy archive PLAN.md

1. Warn if `**Status:**` is not `built` — confirm the user wants to archive anyway.
2. **Rehome the Deferred list.** For each item under the plan's `## Deferred`, verify it against the code before moving it — some will already be done. Move the live ones into the project file's `## Deferred` section (creating it if absent), with the context that makes them intelligible. Strike through and date each item found resolved, the plan's and any in the project file's `## Deferred` that the plan closed, and move it, its text kept, to `.daisy/projects/_deferred-closed/<project>.md` (creating it if absent) under a new heading at the top that names the date and the plan by its id (the timestamp its file name starts with, not a link, which the plan's archive would leave dangling); the project file's `## Deferred` keeps live items only. Then the open items sit in one mutable place instead of being copied into the next plan, where a resolved item keeps looking overdue, and the closed ones stay findable without being re-read at every research phase. An item becomes a `todo.txt` task when it is scheduled, not before.
3. Call `daisy plan archive`
4. Log the archive event to `today.md` via `daisy log`.

## /daisy resume PLAN.md

0. Resolve the plan's real path with `daisy files plan` and write every change below there (rule 17).
1. Read `PLAN.md` fully — note `**Status:**`, completed steps (`[x]`), and the first unchecked step (`[ ]`).
2. **Verify completed work:**
   - Run `git log --oneline -10` to see recent commits.
   - Check today.md for log entries from the previous session.
   - Spot-check 1–2 key files that completed steps claim to have changed — confirm the changes are present.
3. **Read `## Decisions`** in PLAN.md for context recorded by the previous session; if Decisions has no answer to rule 21's question, ask it before step 7.
4. **Identify the interruption point:** Was the previous session stopped mid-step, between steps, or blocked? A step with a commit but no `- [x]` stopped before the orchestrator wrote it into the plan (rule 20), whether before or after its batch's hand-back: verify it as rule 23 says before marking it, and list its decisions, Deferred candidates and open questions under Unknown unless its commits or today.md record them.
5. **Surface gaps:** What context was established during the previous session that is not recorded in PLAN.md?
6. Present a resumption summary to the user:
   - **Completed and verified:** steps done and confirmed in the workspace
   - **Uncertain:** steps marked done but unverified, or partially done
   - **Next:** the step to resume from, and any known sub-state
   - **Unknown:** context that cannot be reconstructed from artifacts
7. Ask: **"Ready to resume from Step N? (yes/no)"** — do not proceed without confirmation.
   If "Uncertain" items are significant (multiple unverifiable steps, or a prior session with a correction history), also offer: "Alternatively, I can compact what's confirmed into a fresh context — say 'compact' to replan from here instead of continuing in-place."
8. If the user says "compact": summarise confirmed work into a Research handoff (exact files changed, decisions made, constraints discovered), write it into the `## Research` section of PLAN.md, reset unchecked steps to reflect remaining work, update `**Status:**` to `planning`, and ask: **"Research summary confirmed — proceed to replan? (yes/no)"**
9. On confirmation to resume: update `**Status:** executing`, then continue from the identified step as `/daisy execute` does, one fresh sub-agent per batch (rule 20).
